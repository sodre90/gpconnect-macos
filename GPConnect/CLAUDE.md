# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this directory (`GPConnect/`). See the repo-root `CLAUDE.md` for the Python `gp-saml-gui` script and the shared privileged helper daemon.

## What this is

A native macOS menu bar (status bar) app plus a companion CLI, both written in Swift, that reimplement the GlobalProtect SAML login flow with `WKWebView` and drive the same privileged helper daemon (`helper/openconnect_helper`) that the Python script uses — no separate root-escalation mechanism was added.

## Build environment: no Xcode, Command Line Tools only

This project is developed and built **without Xcode installed** (`xcode-select` points at Command Line Tools only, so `xcodebuild` is unavailable). Consequences:

- **`./build.sh` is the real build path**, not `xcodebuild`/`Makefile`. It compiles every `.swift` file under `GPConnect/` directly with `swiftc -parse-as-library`, hand-assembles the `.app` bundle (`Info.plist`, `PkgInfo`, `Resources/`), and ad-hoc code-signs it (`codesign --sign - --entitlements GPConnect/GPConnect.entitlements`). It also builds the CLI via `swift build -c release --product gpconnect`.
- `GPConnect.xcodeproj` (generated by `xcodegen generate` from `project.yml`) exists only so SourceKit/editors get proper diagnostics and code completion — it is not used to actually produce the shipped binary. If you add new source files, `xcodegen generate` needs to be rerun for editor tooling to pick them up, but `build.sh` picks up new files automatically via `find GPConnect -name '*.swift'`.
- `Makefile`'s `app`/`install-app` targets call `xcodebuild` and will fail in this environment — `build.sh` is the one that's actually maintained and used.
- Deployment target is macOS 14.0 (`-target arm64-apple-macosx14.0` in `build.sh`), not the 13.0 in `project.yml`/`Info.plist` — SwiftUI's single-argument `.onChange(of:)` used in `IPRangesEditorView.swift` requires 14.0. Keep these in sync if either changes.

Common commands:
```sh
./build.sh                                    # builds .build/app/GPConnect.app and .build/release/gpconnect
open .build/app/GPConnect.app                 # run without installing
cp -R .build/app/GPConnect.app /Applications/ # install app (see permissions gotcha below)
cp .build/release/gpconnect /usr/local/bin/   # install CLI
xcodegen generate                             # regenerate GPConnect.xcodeproj for editor tooling only
```

**Permissions gotcha**: if `/Applications/GPConnect.app` was ever installed via `sudo cp`, it's root-owned, and a later non-sudo `cp -R` to overwrite it will fail with "Permission denied" on extended attributes. Fix: `sudo rm -rf /Applications/GPConnect.app` first, then plain `cp -R` (no sudo needed for a fresh copy into `/Applications`, which perdos owns).

## Why the app doesn't use "obvious" SwiftUI APIs

Several standard SwiftUI menu-bar-app patterns were tried and abandoned during development because they didn't behave correctly here — don't reintroduce them without re-verifying:

- **`MenuBarExtra` + SwiftUI `Window` scenes + `openWindow`**: the original implementation used `MenuBarExtra(.window)` with `Window("SAML Login", id: "saml-auth")` scenes opened via `@Environment(\.openWindow)`. This was unreliable — clicking Connect sometimes opened nothing, and the popover occasionally re-rendered from scratch (showing a loading flash) when reopened. `GPConnectApp.swift` now uses `NSApplicationDelegateAdaptor` with a manually-managed `NSStatusItem` + `NSPopover(.transient)`, and `Services/WindowManager.swift` opens the SAML login and IP-ranges editor as plain `NSWindow`s wrapping `NSHostingView` — both are far more reliable from a menu-bar-app context than the SwiftUI-native equivalents.
- **Sheets over the popover**: SAML auth was originally a `.sheet` presented from `MenuBarView`. A `MenuBarExtra` popover dismisses itself when it loses focus, which killed the sheet the moment the user tried to interact with it. It's now a standalone window via `WindowManager.openSAMLAuth`.
- **`CALayer` rotation for the "connecting" spinner**: an earlier version spun the status item icon with a `CABasicAnimation` on `statusItem.button?.layer`. The button's layer bounds don't align with the visual icon's center, so the icon appeared to orbit an off-center point. The fix in `GPConnectApp.swift` (`startSpinning`/`rotatedImage`) instead redraws the SF Symbol bitmap rotated around its own center at 30fps via a `Timer`, sidestepping the anchor-point mismatch entirely.

## Connection status detection

Do not trust `openconnect`'s stdout text as the sole signal that the tunnel is up — the expected strings (`"Connected as"`, `"ESP tunnel connected"`) don't reliably appear even when the tunnel is genuinely established (confirmed by inspecting `/var/log/openconnect-helper.log` and `ifconfig` while a connection that was "stuck" on Connecting had a fully-functional `utun` interface with routes). `VPNManager.startTunnelPolling()` treats a new `utun*` interface with an IPv4 address (via `Services/NetworkMonitor.swift`'s `activeUtunInterfacesWithIPv4()`, using `getifaddrs`) appearing after connection start as the authoritative "connected" signal, with log-text matching only as a faster secondary path (`markConnected()` is idempotent and guarded on `status == .connecting`).

## Actor isolation

- `VPNManager` and `AppDelegate` are both `@MainActor`.
- `HelperDaemonConnection` (the Unix-socket client) is its own `actor` — calls into it from `VPNManager` that don't need to await a result (e.g. `disconnect()`) must be wrapped in `Task { await conn?.disconnect() }` rather than called directly, since a synchronous `@MainActor` context can't call actor-isolated methods directly.
- The status-item spin `Timer` closure runs on a non-isolated queue; it wraps its body in `MainActor.assumeIsolated { ... }` to touch `@MainActor`-isolated state (`spinAngle`, `statusItem`) without `async`/`await` machinery in a 30fps hot path.

## Config file contract

Both the app (`Models/VPNConfig.swift`) and the CLI (`CLI/main.swift`) read/write the same JSON file at `~/Library/Application Support/GPConnect/config.json`, independently defining matching `Codable` structs (`VPNConfig`/`IPRange` vs. `CLIConfig`/`CLIIPRange`) rather than sharing a module — the CLI is a separate SwiftPM executable target (`Package.swift`) with no dependency on the app target, so the duplication is deliberate, not an oversight. If the JSON shape changes, update both.

## Known limitation: WebAuthn / Touch ID

FIDO2/Touch ID 2FA does not work in the in-app SAML `WKWebView`. It requires the `com.apple.developer.web-browser` entitlement, which needs a real Apple Developer signing identity — ad-hoc signing (`codesign --sign -`, what `build.sh` does) cannot carry that entitlement, and attempting to add it without a matching identity makes the app fail to launch (`Launchd job spawn failed`). This is accepted as a current limitation rather than worked around; password/TOTP-based 2FA works fine.
