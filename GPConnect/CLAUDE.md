# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this directory (`GPConnect/`). See the repo-root `CLAUDE.md` for the Python `gp-saml-gui` script and the shared privileged helper daemon.

## What this is

A native macOS menu bar (status bar) app, written in Swift, that reimplements the GlobalProtect SAML login flow with `WKWebView` and drives the same privileged helper daemon (`helper/openconnect_helper`) that the Python script uses — no separate root-escalation mechanism was added.

A companion `gpconnect` CLI lives in `cli/` as its own SwiftPM package with its own README. It is status/config-only (it cannot connect or disconnect), is not built by `build.sh`, and is not mentioned in the repo-root README on purpose — treat it as an optional extra, but see the config-file contract below.

## Build environment: no Xcode, Command Line Tools only

This project is developed and built **without Xcode installed** (`xcode-select` points at Command Line Tools only, so `xcodebuild` is unavailable). Consequences:

- **`./build.sh` is the real build path**, not `xcodebuild`/`Makefile`. It compiles every `.swift` file under `GPConnect/` directly with `swiftc -parse-as-library`, hand-assembles the `.app` bundle (`Info.plist`, `PkgInfo`, `Resources/`), and ad-hoc code-signs it (`codesign --sign - --entitlements GPConnect/GPConnect.entitlements`). It builds the app only — the CLI is a separate package under `cli/`.
- **Signing must stay the last step, and must target the bundle, not the executable.** It used to sign `Contents/MacOS/GPConnect` before the resources were copied, which sealed an empty `Resources/` — `codesign --verify --deep --strict` then failed with five `file added` errors, and `Resources/helper/install.sh` (which the app runs as root via `osascript`) was outside the seal entirely. Anything that adds files to the bundle therefore has to run *before* the `codesign` call. `build.sh` runs `codesign --verify --deep --strict` immediately afterwards so a future reordering fails the build instead of silently shipping an unsealed bundle; CI runs `build.sh`, so this is enforced there too.
- `GPConnect.xcodeproj` (generated by `xcodegen generate` from `project.yml`) exists only so SourceKit/editors get proper diagnostics and code completion — it is not used to actually produce the shipped binary. If you add new source files, `xcodegen generate` needs to be rerun for editor tooling to pick them up, but `build.sh` picks up new files automatically via `find GPConnect -name '*.swift'`.
- `Makefile` is a thin wrapper: `make app` shells out to `./build.sh` and `make cli` runs `swift build --package-path cli`. It used to call `xcodebuild` and simply failed here. `build.sh` remains the authoritative build path; don't reintroduce `xcodebuild` targets.
- Deployment target is macOS 14.0 (`-target arm64-apple-macosx14.0` in `build.sh`), not the 13.0 in `project.yml`/`Info.plist` — SwiftUI's single-argument `.onChange(of:)` used in `IPRangesEditorView.swift` requires 14.0. Keep these in sync if either changes.

Common commands:
```sh
./build.sh                                    # builds .build/app/GPConnect.app
open .build/app/GPConnect.app                 # run without installing
cp -R .build/app/GPConnect.app /Applications/ # install app (see permissions gotcha below)
swift build --package-path cli -c release     # build the optional CLI (see cli/README.md)
xcodegen generate                             # regenerate GPConnect.xcodeproj for editor tooling only
```

**Permissions gotcha**: if `/Applications/GPConnect.app` was ever installed via `sudo cp`, it's root-owned, and a later `cp -R` to overwrite it will fail with "Permission denied" on extended attributes. Fix: `sudo rm -rf /Applications/GPConnect.app` first, then re-copy the bundle. Whether the copy itself needs `sudo` depends on the machine's account setup — check `test -w /Applications`.

## Why the app doesn't use "obvious" SwiftUI APIs

Several standard SwiftUI menu-bar-app patterns were tried and abandoned during development because they didn't behave correctly here — don't reintroduce them without re-verifying:

- **`MenuBarExtra` + SwiftUI `Window` scenes + `openWindow`**: the original implementation used `MenuBarExtra(.window)` with `Window("SAML Login", id: "saml-auth")` scenes opened via `@Environment(\.openWindow)`. This was unreliable — clicking Connect sometimes opened nothing, and the popover occasionally re-rendered from scratch (showing a loading flash) when reopened. `GPConnectApp.swift` now uses `NSApplicationDelegateAdaptor` with a manually-managed `NSStatusItem` + `NSPopover(.transient)`, and `Services/WindowManager.swift` opens the SAML login and IP-ranges editor as plain `NSWindow`s wrapping `NSHostingView` — both are far more reliable from a menu-bar-app context than the SwiftUI-native equivalents.
- **Sheets over the popover**: SAML auth was originally a `.sheet` presented from `MenuBarView`. A `MenuBarExtra` popover dismisses itself when it loses focus, which killed the sheet the moment the user tried to interact with it. It's now a standalone window via `WindowManager.openSAMLAuth`.
- **`CALayer` rotation for the "connecting" spinner**: an earlier version spun the status item icon with a `CABasicAnimation` on `statusItem.button?.layer`. The button's layer bounds don't align with the visual icon's center, so the icon appeared to orbit an off-center point. The fix in `GPConnectApp.swift` (`startSpinning`/`rotatedImage`) instead redraws the SF Symbol bitmap rotated around its own center at 30fps via a `Timer`, sidestepping the anchor-point mismatch entirely.

## Connection status detection

Do not trust `openconnect`'s stdout text as the sole signal that the tunnel is up — the expected strings (`"Connected as"`, `"ESP tunnel connected"`) don't reliably appear even when the tunnel is genuinely established (confirmed by inspecting `/var/log/openconnect-helper.log` and `ifconfig` while a connection that was "stuck" on Connecting had a fully-functional `utun` interface with routes). `VPNManager.startTunnelPolling()` treats a new `utun*` interface with an IPv4 address (via `Services/NetworkMonitor.swift`'s `activeUtunInterfacesWithIPv4()`, using `getifaddrs`) appearing after connection start as the authoritative "connected" signal, with log-text matching only as a faster secondary path (`markConnected()` is idempotent and guarded on `status == .connecting`).

## Actor isolation

- `VPNManager` and `AppDelegate` are both `@MainActor`.
- `HelperDaemonConnection` (the Unix-socket client) is its own `actor` — calls into it from `VPNManager` that don't need to await a result (e.g. `disconnect()`) must be wrapped in `Task { await conn?.disconnect() }` rather than called directly, since a synchronous `@MainActor` context can't call actor-isolated methods directly.
- The status-item spin `Timer` closure runs on a non-isolated queue; it wraps its body in `MainActor.assumeIsolated { ... }` to touch `@MainActor`-isolated state (`spinAngle`, `statusItem`) without `async`/`await` machinery in a 30fps hot path.

## Versioning

The repo-root `VERSION` file is the single source of truth. `build.sh` stamps it into the built bundle's `CFBundleShortVersionString`/`CFBundleVersion` via `PlistBuddy` (the values in `GPConnect/Info.plist` are `0.0.0-dev` placeholders), and `make version` regenerates `cli/Sources/gpconnect-cli/Version.swift` from it. That generated file is committed so a bare `swift build` in `cli/` still works; CI re-runs `make version` and fails on `git diff --exit-code` if it's stale. To cut a release, bump `VERSION`, run `make version`, commit, then tag.

## Config file contract

Both the app (`GPConnect/Models/VPNConfig.swift`) and the CLI (`cli/Sources/gpconnect-cli/main.swift`) read/write the same JSON file at `~/Library/Application Support/GPConnect/config.json`, independently defining matching `Codable` structs (`VPNConfig`/`IPRange` vs. `CLIConfig`/`CLIIPRange`) rather than sharing a module — the CLI is a separate SwiftPM package (`cli/Package.swift`) with no dependency on the app target, so the duplication is deliberate, not an oversight. If the JSON shape changes, update both.

This duplication is load-bearing, not cosmetic: the CLI's `saveConfig` re-encodes the *whole* file on `config set` and every `ranges` subcommand, so a `gpconnect` binary that predates a newly-added `VPNConfig` key will silently strip that key from the user's config. Keeping the CLI out of `build.sh` makes a stale binary more likely, so rebuild and reinstall it whenever `VPNConfig` gains a field.

## Privileged helper auto-install

`Services/HelperInstaller.swift` lets the app offer to install the privileged helper daemon itself instead of
requiring the user to run `sudo helper/install.sh` in a terminal. `build.sh` copies `../helper/{install.sh,
uninstall.sh,openconnect_helper,com.openconnect.helper.plist}` into `Contents/Resources/helper/` at build time
(see the "Bundle the privileged helper daemon" step). At runtime, `HelperInstaller.install()` locates
`install.sh` via `Bundle.main.url(forResource:withExtension:subdirectory:)` and runs it through
`osascript -e 'do shell script "..." with administrator privileges'` — this shows a native macOS admin-password
dialog without requiring `SMJobBless`/Service Management entitlements, which (like the WebAuthn entitlement
below) would need a real Apple Developer ID this project doesn't have. `install.sh`'s own internal `sudo`
calls are harmless no-ops here since the whole script is already running as root under the AppleScript
elevation.

Because that script executes as root, it is deliberately covered by the bundle's code signature (see the
signing-order note above) so `codesign --verify --deep --strict` detects a modified `install.sh`. Note the
limit of this with ad-hoc signing: an attacker who can write to the bundle can also re-sign it ad-hoc, since
`--sign -` requires no identity. The seal reliably catches accidental or careless modification and is a
prerequisite for real Developer ID signing, but only a notarized, Gatekeeper-enforced signature would make
this a genuine integrity guarantee.

`AppDelegate.applicationDidFinishLaunching` calls `promptToInstallHelperIfNeeded()` once per launch if
`HelperInstaller.isInstalled` (checks for the socket file) is false; `SettingsView` also exposes a manual
"Install Helper" button for when the user dismisses that prompt or the daemon later goes away.

## Known limitation: WebAuthn / Touch ID

FIDO2/Touch ID 2FA does not work in the in-app SAML `WKWebView`. It requires the `com.apple.developer.web-browser` entitlement, which needs a real Apple Developer signing identity — ad-hoc signing (`codesign --sign -`, what `build.sh` does) cannot carry that entitlement, and attempting to add it without a matching identity makes the app fail to launch (`Launchd job spawn failed`). This is accepted as a current limitation rather than worked around; password/TOTP-based 2FA works fine.
